Operating window: 7 November 2026 through 4 February 2027 inclusive (90 days). This is a working amendment to the 12 September 2026–12 March 2027 [organic growth plan](growth-plan-2026-09-12.md), informed by the [November 7 editorial record](research/content-quality-review-2026-11-07.json). Preserve existing topic IDs, dated assignments and local master keywords when available. Do not overwrite the private original calendar. Use this plan to decide whether an item should ship. If a local schedule conflicts, record the difference and keep the stricter evidence and deduplication gates.

## Decisions and measurement

Primary customer: overseas B2B buyer planning a custom fragrance, discovery or rigid presentation box. The second cluster is collapsible or magnetic rigid packaging, with inserts and freight comparisons. Use jewelry, paper bags and sustainability as supporting paths when relevant. Trade show conversations may identify buyer questions; only independently sourced, permission-cleared MTT materials belong on MTT. Keep the published 1,000 pieces/design policy pending a documented change by MTT. Public pages omit supplier rates, private budgets and identities. Goals are qualified enquiries, quote requests and samples; no commitment to Google or AI visibility.

- Log complete 28-day GSC periods (property, last available date, countries, landing pages, non-brand terms); use complete seven-day periods for operational checks. Distinguish clicks, GA4 accepted forms, WhatsApp clicks, inbox receipts, qualified briefs, quotations, approved samples and orders. A qualified brief is a genuine identified business with a plausible packaging need and a quantity or timing; consolidate repeat contacts for one project. Keep this private. Compare counts and denominators; no data means unknown.
- Use GSC Search Generative AI impressions and pages, Bing Webmaster Tools AI Performance citations, and Clarity or GA4 aggregate behavior subject to consent. Separate trade show QR/UTM traffic and organic results. Preserve the active analytics stream, Formspree and existing events. Use mocked delivery tests for engineering; confirm receipt from a legitimate enquiry with the operator.
- Historical tool requests included claude-seo, geo-seo-claude, claude-blog, localseoskills and seo-skill. Only use verified installed capabilities; check access at run time. Official guidance and first-party evidence prevail over tool scores. No new paid subscriptions.

## Daily packaging updates

Each run first reads the latest remote main, production revision, pending PRs and recent dated reviews, plus any accessible private calendar and the previous run. Claim one date, one issue and one destination URL per meaningful change. The repository documents a 09:00 Shanghai local heartbeat; its present state must be checked where possible. The subsequent cloud review first checks whether the local run already handled the day's sources or target. Reuse its pending work or skip, never create a parallel change for the same story. A push/deployment is evidence of output, not of an entire daily review. Do not add another GitHub cron.

Review first-party updates since the last successful check: regulators, original brand product/fulfilment pages, board or material manufacturers and new technical guidance. Record publication date, event or effective date, geography, source URL and verification time. Use a seven-day catch-up only when justified and identify older material. Offers, publication dates, test claims and launch dates must remain distinct. Do not republish source photos or copy paragraphs.

1. Match the event to a buyer decision and previously published coverage. Prefer updating a commercial landing page or guide. If it changes no specification, test, sourcing decision, shipping or reporting action, log the finding and leave the site alone. A daily check does not require publication.
2. A new article needs a distinct intent, verifiable primary evidence and original practical value. Apply the existing [quality pipeline](content-quality-pipeline.md), score at least 85/100, no unresolved factual issue. Maximum two genuinely new guides over any rolling seven days for this overlay. While above cap, improve existing content. No quota for edits. Keep legitimate concepts, third-party references, anonymised quotations and documented production cases labeled separately.
3. Update the interface only where a buyer cannot find, compare or enquire effectively; record reproduction, impacted route and mobile/desktop checks. Adjust architecture for sustained query/intent overlap, an orphan or a broken path. Preserve URLs where possible. Any necessary move requires a redirect map and canonical, sitemap, internal link and multilingual checks; no domain/CDN/DNS changes.
4. Use a scoped branch, preferably one open daily PR, protect other branches and verify exact diff. Run established build, lint, types, mocked enquiry and relevant UI/SEO checks. Publish approved and validated changes only via the existing main → GitHub Pages pipeline. Verify deployment revision, live page, HTTP/canonical and a changed-URL notification if applicable. Record failures without claiming a release; do not auto-merge unrelated or explicitly held PRs, including PR #2.
5. Capture source, affected URL, what changed, evidence/score, commit/PR, verified production SHA or blocked state, dated next check. A no-change day needs only a private execution entry; it must not alter a page date or trigger indexing. Send a weekly compact report of business and technical evidence, including missing data.
